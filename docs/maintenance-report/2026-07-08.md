## Security Review

### Application Security

- No authentication, authorization, session handling, or server-side API surface
  exists (fully static site) — reviewed and not applicable.
- The only user-input surface is the contact form, which posts directly to a
  third-party form backend (Formspree) over HTTPS; no client-side handling of the
  submitted data occurs on this site.
- Searched all HTML/CSS/JS for hardcoded secrets, API keys, tokens, and credentials
  — none found.

### Configuration Security

- No environment variables, `.env` files, or secrets are used anywhere in the
  repository.
- `_config.yml` contains only a GitHub Pages theme name; no sensitive configuration.
- No debug flags or unsafe defaults present.

### Infrastructure Security

- **Finding (fixed)**: `404.html` loaded Bootstrap **3.3.7** from `cdnjs.cloudflare.com`
  with no Subresource Integrity (SRI) hash — an outdated library version plus an
  unpinned third-party script/style dependency (supply-chain risk: if the CDN or
  the specific file were ever compromised, the served CSS could be swapped without
  any integrity check). **Fix**: replaced with the locally vendored, already-audited
  Bootstrap 4.6.0 build (`Content/bootstrap.min.css`), removing the external
  dependency and the outdated-version exposure in one change.
- No CI/CD pipeline existed prior to this audit (see CI/CD section) — added basic
  automated validation to catch regressions (broken markup, broken internal links)
  before they reach the deployed site.
- Repository has no deployment credentials, container images, or cloud
  configuration to review — GitHub Pages handles deployment automatically from the
  default branch.

## Code Quality

### Findings

- **Dead code (removed)**: `Content/bootstrap-grid.css(.map)`, `Content/bootstrap-grid.min.css(.map)`,
  `Content/bootstrap-reboot.css(.map)`, `Content/bootstrap-reboot.min.css(.map)`,
  `Content/bootstrap.css`, and `Content/bootstrap.css.map` were vendored but never
  referenced by any HTML file (`index.html` uses the "Hola" theme's own CSS, not
  Bootstrap). Removed ~900 KB of unused, unreferenced files. Kept
  `Content/bootstrap.min.css` + its source map, which are now actively used by
  `404.html`.
- **Invalid markup (fixed)**: `404.html` had a `<style>` block placed between the
  opening `<html>` tag and the `<head>` tag, causing browsers to implicitly open a
  second `<head>` element (confirmed via HTML5 validator: "Start tag `head` seen but
  an element of the same type was already open"). Moved the `<style>` block inside
  `<head>`, after the existing `<link>` tags. Purely a markup-correctness fix — no
  visual change (verified via screenshot comparison).
- **Informational — commented-out dead code** (left as-is, no action needed):
  `index.html` contains a few intentionally-disabled features left as HTML
  comments — a "New" nav link to a non-existent `index2.html`, a resume-download
  button pointing at a missing `Content/File/resume_reo.pdf`, and a
  `Content/Hola/js/music.js` script include. None of these render or execute since
  they're inside comments, so there is no live broken link or functional bug.
  Flagged here for visibility in case the owner wants to either finish or remove
  these features later; not touched in this pass to avoid guessing at intent.
- **Known limitation (documented, not fixed)**: `index.html` has several HTML5
  validation errors inherited from its third-party "Hola" theme template
  (misplaced `alt` attribute on a `<section>`, `<div>` nested inside `<h1>`/`<h3>`,
  an unclosed `<div>`). All browsers recover from these gracefully via standard
  HTML5 error-recovery parsing (confirmed via rendered screenshot — page displays
  correctly), so this was not treated as a launch-blocking issue. Fixing it
  properly would mean restructuring a large, unfamiliar third-party template,
  which is a bigger, higher-risk change than warranted for a routine maintenance
  pass. Recorded as tracked tech debt; the new CI HTML-validation job intentionally
  scopes to `404.html` only for now so it doesn't block merges on this pre-existing
  issue.

- **Repository hygiene (fixed)**: `debug.log` (a stray Chromium `settings.cc`
  internal error log, unrelated to the site) was accidentally committed to the
  repository root. Removed it and added `debug.log` to `.gitignore` to prevent
  recurrence.

No refactoring was performed beyond the fixes above — the codebase is otherwise a
straightforward static site with no significant technical debt.

## CI/CD

- **Added**: `.github/workflows/ci.yml` — no CI/CD pipeline existed previously.
  - `validate-html`: runs `html5validator` against `404.html` on every push/PR to
    `main`.
  - `check-links`: runs `lychee` (offline mode) against `index.html` and `404.html`
    on every push/PR to `main`, catching broken internal links/asset references
    such as the kind of link that this maintenance pass could have introduced.
- Both jobs are required-check candidates; recommend enabling GitHub branch
  protection on `main` to require these checks before merge (not configured as
  part of this change, since branch protection is a repository-settings change,
  not a code change).
- Deployment itself remains fully automatic via GitHub Pages; no deploy job was
  added since none is needed.
